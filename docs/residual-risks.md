# Residual risks

The register of what remains after the controls in `spec/SPEC.md` and `docs/threat-model.md`, and what is not proven. Each entry gives a status and the mitigation that exists today. "Open" means no mitigation exists in the repo. Nothing here has been independently reviewed; see R17.

Status values: **By design** (a stated non-guarantee), **Partial** (a mitigation exists with a known gap), **Open** (no mitigation in the repo), **Unverified** (claimed but not tested in this repo).

## Enforcement scope

**R1. Uninstrumented paths are outside the guarantee.** Direct database, cache or vector-store reads, and model calls made without the wrapper, are not checked. `benchmark/reports/latest.md` says the same. *Status: By design. Mitigation: wrap every read path (`docs/integration-guide.md`); `docs/coverage-matrix.md` lists only the adapters the conformance suite exercised. Nothing in the repo detects a bypass at runtime.*

**R2. Model-gateway coverage depends on the `untracked` mode and on exempt roles.** `sdk-python/ales_sdk/model_gateway.py` cannot authorize items that carry no ALES id. `GuardedModelCall(untracked=...)` defaults to `"protected"`: untracked non-exempt items are removed (reported in `PreparedContext.blocked_untracked`, reason `UNTRACKED_CONTEXT`). `"deny"` is an alias with the same semantics; `"error"` raises `UntrackedContextError` with the item indices; `"allow"` is an explicit opt-out that passes them through unchecked, counts them in `DecisionSummary.untracked`, and logs a one-time warning per instance. Items whose `role` is in `exempt_roles` (default `("system",)`) are the caller's own prompt and are never offenders; exempting `"user"` would defeat the control. An item carrying any `ales_*` metadata key is never exempt, whatever role it claims, and `trusted_roles_source="none"` disables role exemption entirely. Under FailMode.OBSERVE nothing is blocked in any mode except as observed (counted as `observed_only`). *Status: Resolved-with-default (protected by default). Residual: content a caller places in an exempt role without any ALES marker is still not authorized; use `trusted_roles_source="none"` if roles can be influenced by untrusted parties.*

**R3. Information already disclosed cannot be recalled.** Content already read by a person or sent to a model is not removed by revocation. *Status: By design (SPEC non-guarantee). Mitigation: classification, short expiry and narrow scopes limit what is disclosed in the first place.*

**R4. No neural attribution.** A model response built from N prompt sources records all N as parents. Over-attribution is intended; the system cannot say which source influenced which token. *Status: By design.*

**R5. Prompt injection inside an allowed context is not detected.** Trust state tracks lineage, not content. *Status: By design (threat model row 3).*

## Staleness and timing

**R6. A disconnected reader can serve a cached ALLOW up to the cache TTL after a revocation, and an in-flight call can deliver one that was computed just before it.** Total client exposure = (a) the duration of an authorize call that was already past its lineage read when the revocation committed + (b) the SDK decision-cache TTL if that ALLOW was cached. (a) is measured in `stress/test_inflight_revocation.py` (50 revocations x 4 tight-loop readers, SQLite and Postgres, `-s` prints `[inflight-bound]`): zero ALLOWs from reads that started after `accept()` returned; ALLOWs delivered after acceptance (computed before it) arrived at most 23 ms (Postgres) / 60 ms (SQLite) late, never later than the end of their own call (slowest observed call 0.67 s under contention). A deterministic freeze test shows the stale window equals the in-flight remainder (50 ms hold -> 52 ms; 250 ms -> 252 ms). Such a late ALLOW is stamped with the pre-revocation `revocation_epoch` (the epoch is read before the lineage), so an epoch-keyed cache invalidates it on its next epoch observation. The SDK `max_ttl` defaults to 30 s and clock skew allowance 30 s. A reader that cached an ALLOW before a future-dated event was accepted and never contacts the server again serves that entry until TTL; responses without `valid_until` (v0.2 servers) give no earlier cutover. *Status: Partial. Bound: in-flight call duration + TTL; not zero.*

**R7. Cross-process decision-cache staleness is bounded by TTL; the in-flight part is measured, the cross-replica part is not.** A reader in another process that did not see the new epoch may serve a cached ALLOW until its next server contact or the TTL. The server-side in-flight component is measured (R6) and holds across processes sharing one database because it rests on the database commit, not on process memory. RevocationBench readers still share the revoking client, so SDK-cache propagation across replicas is not exercised there. *Status: Partial (server in-flight window measured; cross-replica SDK propagation bounded by TTL, not measured). Mitigation: TTL of 30 s.*

**R8. Exposure in BOUNDED_OFFLINE equals the lease plus acceptance delay plus the in-flight window.** Default `ALES_SNAPSHOT_LEASE` is 60 s, and the SDK `offline_lease_seconds` default is 60 s. The in-flight authorize window (R6, tens of ms measured) adds to, and is negligible against, the lease. The window is published, not zero. *Status: By design (guarantees G4). Mitigation: set the lease deliberately and publish it.*

**R9. Clock skew.** Clients with badly skewed wall clocks are protected only up to the 30 s skew allowance. The server-side race measurements in R6 use a single monotonic clock and do not model client skew; client exposure is the in-flight window plus TTL plus up to the skew allowance. *Status: Partial.*

## Purge and cleanup

**R10. Purge handlers are log-only unless the operator configures `ALES_PURGE_TARGETS`.** The shipped app builds a `PurgeRegistry` from the `ALES_PURGE_TARGETS` JSON list (redis cache, Qdrant, pgvector targets; `server/ales_server/purge_config.py`) and wires it into the outbox worker. `ALES_PURGE_POLICY` (`purge` default, or `deny-only`) makes the choice explicit: under `ALES_ENV=production`, policy `purge` with no targets is a startup violation, so the server no longer silently runs log-only; `deny-only` starts with one prominent warning that revoked bytes remain in stores until purged externally and `GET /v1/outbox/stats` reports `worker.handlers: "deny_only"`. Development keeps the log-only default. Use-time denial holds in every mode because it depends on tombstones, not purge. Configured targets with a missing `ales_adapters` import or client library are a startup `ConfigError`. Only the store kinds you list are purged; a row whose kind has no target stays `pending` (visible in `/v1/outbox/stats`). *Status: Resolved-with-config (production refuses silent log-only; the operator must either configure `ALES_PURGE_TARGETS` or accept `deny-only` explicitly and purge externally). `python -m ales_server.preflight` reports the chosen mode. See `docs/operations.md` section 4.*

**R11. Dead letters need an operator.** Rows that exhaust six attempts stay `dead`. `GET /v1/outbox/dead` (admin) lists the caller's tenant's dead rows (id, context_id, version, store_kind, attempts, last_error, created_at) and `POST /v1/outbox/dead/{id}/requeue` (admin, audited as `admin.outbox.requeue`) returns one to `pending` with its attempts reset; `POST /v1/outbox/run` (admin) runs the dispatcher once for the caller's tenant. All three are tenant-scoped; another tenant's row is a 404. *Status: Partial (recovery API exists; nothing requeues automatically, and no alert is wired to the `dead` count). Mitigation: alert on `dead` in `/v1/outbox/stats` or `/v1/metrics`, fix the store, then requeue.*

**R12. Purge timing and real-store behaviour are measured only against stand-ins.** The benchmark's purge latency excludes the worker's poll interval, real store latency and retries. Purge is now verified: after each target's idempotent delete the wiring re-checks that the object is gone (cache data key and reverse index, Qdrant point, pgvector row; version-aware, so a newer version under the same `context_id` is neither deleted nor treated as a failure) and raises if it is still present, so the outbox retries; with at-least-once delivery that makes purge verified at-least-once. Verification is a read-after-delete against the same store, so an eventually consistent replica, or a store that acknowledges deletes it has not applied, can still pass it. *Status: Partial. Under `ALES_PURGE_POLICY=deny-only` no purge is attempted by this server at all (R10). No latency measurement against live Qdrant, pgvector or redis has been recorded.*

## Identity and ingress

**R13. Identity revocation is bounded, not instant.** `server/ales_server/oidc.py` accepts RS256 and ES256 JWTs (`exp` required) from a static JWKS (`jwks`, `jwks_file`) or a live `jwks_uri`. A `jwks_uri` is fetched over https (plain http only for 127.0.0.1/localhost), cached for `ALES_OIDC_JWKS_TTL` (300 s), refetched on an unknown `kid` at most once per `ALES_OIDC_JWKS_MIN_REFRESH` (30 s), and kept serving from cache after a failed fetch for at most `ALES_OIDC_JWKS_MAX_STALE` (3600 s) before every token is refused; with no cache a fetch failure is a 401. A key withdrawn at the IdP stays trusted until the cache refreshes (up to the TTL, or longer while fetches fail, up to the max-stale bound). Individual identities and tokens are revocable without a restart through `ALES_DENYLIST_FILE` (`subjects`, `jwt_subs`, and per-token `jwt_jtis` matched against the `jti` claim) and `ALES_TOKENS_FILE`: both are hot-reloaded, stat-ed at request time at most once per 5 s, so the bound is the reload interval (<= 5 s) plus requests already in flight when the file changed; a malformed reload keeps the last good content. `jti` is optional per RFC 7519: a token without one cannot be listed, so set `"require_jti": true` in `ALES_OIDC_CONFIG` to reject such tokens. Without a denylist entry a token stays valid until `exp`. Tokens verified on a replica that has not yet re-read a shared file (for example a delayed volume sync) stay valid there until it does. A JWKS cache miss blocks other verifications on that replica for up to the 5 s fetch timeout. *Status: Partial (revocation bound <= 5 s plus in-flight, per subject and per token; IdP key withdrawal still waits for the JWKS cache). Mitigation: keep token lifetimes short, require `jti`, lower `ALES_OIDC_JWKS_TTL` if faster key withdrawal matters, stop issuance at the IdP, and distribute the denylist file to every replica together.*

**R14. Key revocation at ingress is not retroactive, as far as the repo shows.** `PATCH /v1/admin/keys/{key_id}` with `status=revoked` affects the signature check at ingress (`_enforce_signature`). This review did not find code that revokes objects already registered under that key. *Status: Unverified. Mitigation: after revoking a key, submit revocation events for the sources it issued.*

**R15. Signatures prove issuer, not truth.** A connector with a valid signing key can publish false but correctly signed envelopes. *Status: By design (SPEC signing section).*

**R16. Signatures are off by default in config.** `ALES_REQUIRE_SIGNATURES` is still off when unset in development. With `ALES_ENV=production` (the `deploy/Dockerfile` default) `create_app()` refuses to start with signatures off unless `ALES_ALLOW_UNSIGNED_INGRESS=1` is set explicitly (logged as a warning). Helm sets signatures on. *Status: Mitigated for production-mode deployments (startup refusal, test-covered). Residual: a deployment that does not set `ALES_ENV=production` (bare `uvicorn` outside the Dockerfile; the Helm chart sets it from `config.env`, default `production`, via `templates/configmap.yaml`) keeps the old default, and the explicit override remains available.*

## Deployment

**R17. No third-party security review is recorded in this repo.** The repo contains internal assessment material and remediation commits (`ENGINEERING_ASSESSMENT.md`, commit `633f891`). They are not an external review. Dependency vulnerability scanning (`pip-audit`, `npm audit`), a CycloneDX SBOM artifact and a gitleaks secret scan now run in `.github/workflows/supply-chain.yml` on push, PR and weekly. These are automated supply-chain checks, not a review of the design or code; no independent penetration test or audit exists, and the workflow has not yet run on a real GitHub runner. *Status: Partial (scanning and SBOM in CI; independent pentest absent).*

**R18. Terraform and Helm templates are CI-validated but have not been applied to real clouds or a cluster.** The `deploy-validate` CI job runs `terraform fmt -check`, `terraform init -backend=false` and `terraform validate` on every module and `helm lint` + `helm template` on the chart with real tools; no `terraform apply` or `helm install` against a live environment has been performed. *Status: Partially verified. Mitigation: perform a real deployment in a non-production environment before relying on the templates.*

**R19. Migration race on concurrent startup.** `run_migrations` has no lock in the repo. Concurrent replicas against a database behind head can race. The Helm hook Job avoids this for Helm releases only. *Status: Partial. Mitigation: hook Job, or one replica first. `ALES_SKIP_STARTUP_MIGRATIONS` exists in code (see R20).*

**R20. Documentation said `ALES_SKIP_STARTUP_MIGRATIONS` did not exist.** `server/ales_server/main.py` reads it. `deploy/README.md` and `deploy/helm/ales-invariant/templates/NOTES.txt` now describe it. *Status: Resolved (documentation corrected). The chart still does not set it; `docs/operations.md` sections 1 and 3 document the switch.*

**R21. Rolling upgrade readiness is untested.** `/v1/readyz` requires the database revision to equal the running image's head. Old pods become NotReady once migration `0002` or later runs. *Status: Unverified. Mitigation: `docs/upgrades.md`; test in staging.*

**R22. Restore can resurrect revoked sources.** A point-in-time restore to before a revocation removes the event, tombstones and epoch bump, so the source is allowed again until the revocation is re-applied. `scripts/ales_restore_check.py` closes this with a procedure: `export` writes every revocation event, tombstone and per-tenant epoch as JSON lines (run it on a schedule to storage the database operator cannot rewrite); after any restore, `verify` compares that file (or an `ALES_AUDIT_EXPORT_FILE` audit export) with the database and exits 1 on any missing event, tombstone or lagging epoch; `reapply` re-accepts every missing event idempotently by `event_id`. *Status: Mitigated with procedure (runbook: `docs/operations.md` section 8). It is only as good as the operator's discipline: events accepted after the last export and lost with the database are not in the file; the repo does not schedule the export; events re-applied from an audit export are unsigned and lack `source_event_id`; `reapply` must run before the control plane serves traffic; objects registered after the restore point are lost in any case. Downstream stores still need a re-purge (R10).*

**R23. Audit tail truncation is not detectable from the chain.** The chain alone cannot show that its tail was cut. `GET /v1/audit/head` (read role) now returns `{tenant_id, seq, head_hash, at}` for external anchoring, and `GET /v1/audit/verify` no longer writes to the ledger. Optional `ALES_AUDIT_EXPORT_FILE` writes every committed audit record as one JSON line to an append-only file (best effort: failures are logged and counted in `ales_audit_export_failures_total`, never fail the request). *Status: Partial. The endpoint and the export hook exist and are tested; the anchoring itself is still an operator task. The export file protects against tail truncation only if it lives on storage that an attacker with database access cannot rewrite (separate host, WORM or append-only mount), and nothing in the repo schedules or verifies anchors. Mitigation: poll `/v1/audit/head` on a schedule into WORM storage; alert on anchor gaps or on a head that does not extend the previous anchor.*

**R24. Docs said the container runs as root.** `deploy/Dockerfile` sets `USER 10001:10001` and installs runtime dependencies only. The deploy docs are corrected. *Status: Resolved (documentation corrected). Confirm the container user on the image you deploy.*

**R25. Insecure defaults if env is misconfigured.** In development an unset `DATABASE_URL` uses a SQLite file, an unset `ALES_SNAPSHOT_KEY` uses an ephemeral key, and `ALES_DEV_ALLOW_ANONYMOUS=1` with no tokens grants all roles; development mode now logs one conspicuous startup banner listing each unsafe setting in effect. With `ALES_ENV=production`, `create_app()` raises one `ConfigError` naming every violation at once: no tokens and no OIDC, `ALES_DEV_ALLOW_ANONYMOUS` set at all, signatures off, no persistent snapshot key, SQLite, or `ALES_ENFORCE_WORKLOADS=off` (which defaults to `strict` there). *Status: Mitigated when `ALES_ENV=production` is set (Dockerfile default); the guard is opt-in by environment variable, so a process started without it stays in development behaviour. The Helm chart sets `ALES_ENV` from `config.env` (default `production`), so Helm releases get the guard unless an operator overrides `config.env`.*

**R26. Ephemeral snapshot key override.** `ALES_ALLOW_EPHEMERAL_SNAPSHOT_KEY=1` lets a server start with a per-process key. In production mode a persistent key is now required regardless of the signature setting, and this override (logged as a warning) is the only way around it; `ALES_ALLOW_UNSIGNED_INGRESS=1` and `ALES_ALLOW_SQLITE=1` are the sibling explicit overrides. *Status: By design (explicit, logged override). Mitigation: do not set any of the three outside dev; alert on the startup warnings.*

**R27. Metrics are per process; the public scrape shows cross-tenant sums.** `GET /v1/metrics` (read role) renders Prometheus text. Counters are per process and reset on restart, so the scraper must sum across replicas. `ALES_METRICS_PUBLIC=1` exempts the path from auth and then renders totals over all tenants. The Helm ServiceMonitor is disabled and sends no bearer token. *Status: Partial (resolved with caveats). Mitigation: scrape each replica with a read token and aggregate with `sum()`; keep `ALES_METRICS_PUBLIC` off; restrict network access to the endpoint (`docs/operations.md` section 6).*

## Evidence limits

**R28. Benchmark evidence covers real Postgres and HTTP on one machine, not multi-replica, cross-region or sustained load.** RevocationBench has two profiles (`python -m revocationbench --profile inprocess|postgres`). The in-process profile (reports `benchmark/reports/latest.*`) uses the FastAPI TestClient and in-memory SQLite. The postgres profile (reports `benchmark/reports/latest-postgres.*`) runs the control plane as a real `uvicorn` subprocess against a throwaway Postgres 16 database, SDK clients over loopback HTTP, and a real Redis (via `GuardedCache` and the cache purge handler) for the cache scenarios; each report row records its `profile`, `database` and `transport`. Each run is against the git revision recorded in its report header, on one Windows machine with Postgres and Redis in Docker containers on the same host. The checked-in reports record 0 escapes in 387 post-revocation read attempts across 13 scenarios and 0 false blocks. Latency figures, including the Postgres profile's authorize, revocation and purge percentiles, are in the report headers and aggregate tables; the Postgres profile makes every `authorize` a server round trip over loopback HTTP with Docker port-forwarding. The scale scenarios (a 100-deep derivation chain and a 200-child fan-out) are in the scenario notes of both reports. They show that lineage reads grow with depth, and that purge is enqueued inside the revocation transaction. `service_outage` (transport kill) and `delayed_revocation` (server clock shift) need in-process tricks and always run on the in-process profile; the postgres report marks them `inprocess`. These numbers are dominated by the host's Docker-to-Windows networking and are relative, not absolute. Still not covered: multiple replicas behind a load balancer, cross-host and cross-region latency, TLS, sustained or concurrent load and connection-pool pressure, a real vector store (the purge target for vector kinds is an in-memory stand-in), and the background outbox worker (disabled in the benchmark). *Status: Partial. Mitigation: rerun at the release revision on production-like infrastructure with multiple replicas and concurrent load.*

**R29. Concurrency is covered on a single host; multi-replica, partition and sustained-load behaviour is not.** Covered by `stress/` (`pytest -q stress`; SQLite, and Postgres when `TEST_POSTGRES_URL` is set): readers racing a revocation with no ALLOW from a read started after acceptance (`test_concurrent_revoke_read.py`), the in-flight bound (`test_inflight_revocation.py`, R6), concurrent registration and revocation submission (`test_concurrent_registration.py`), gap-free per-tenant epochs and audit chain under concurrent writers (`test_epoch_monotonic.py`), two real server processes over one database with a bounded cached ALLOW (`test_multiprocess.py`), two outbox dispatchers racing with exactly-once leasing (`test_outbox_contention.py`), and an adversarial second tenant plus a read-only credential walking the route table (`test_tenant_adversarial.py`, R31). Not covered: multiple replicas behind a load balancer, network partitions between replicas and the database, sustained or high-concurrency load and connection-pool pressure, and traversal cost on graphs with both depth and width (only a 100-deep chain and a 200-child fan-out are measured). RevocationBench itself is sequential; its reports say so. *Status: Partial. Mitigation: run `stress/` and the postgres benchmark profile on production-like infrastructure with several replicas before relying on cross-replica figures.*

**R30. Lineage completeness depends on callers.** Derivatives created through uninstrumented paths have no parent and cannot be denied. Lineage supplied by an untrusted caller is only as good as that caller. *Status: By design (threat model assumptions).*

**R31. Storage-level tenant isolation is not provided.** Tenancy is enforced in the application (`bind_tenant`, tenant-scoped graph/approval/policy/workload queries). `stress/test_tenant_adversarial.py` (SQLite and Postgres) tests what that covers: a foreign-tenant `context_id` returns exactly the wire answer of an unknown id (`UNKNOWN`/`OBJECT_UNKNOWN`; the `tenant_mismatch` flag is recorded only in the caller's own audit detail); lineage, approval, policy, workload, grant and delegation lookups, decisions and mutations on another tenant's ids answer 404 or empty; a foreign revocation event cannot affect another tenant; metrics, audit head/verify and snapshots are scoped to the credential's tenant; a read-only credential gets 403 on every non-read route in the OpenAPI table. It does not cover a bug that bypasses the application layer (a missing `tenant_id` predicate in a future query, direct database access, a shared database role): all tenants share one schema and one database credential, and Postgres row-level security is deliberately not implemented. *Status: By design (threat model row 4). Recommended for strict deployments: one database (or at minimum one schema and database role) per tenant, i.e. one control-plane instance per tenant pointing at its own database, so that isolation does not depend on application predicates alone.*

**R32. S3 connector digests are ETag identities, not content hashes.** Envelope `content_digest` for objects not streamed is `sha256("s3-etag:" + etag)` (`connectors/ales_connectors/s3_source.py`). Multipart uploads with different part sizes give a different ETag, which yields a spurious supersession (the safe direction). SSE-KMS and SSE-C ETags are not content hashes, so a content change that does not change the ETag may go undetected. `S3Connector(digest_mode="content")` now streams and sha256-hashes every object regardless of size or encryption, closing the gap at the cost of one full GET per new or changed object (egress, request and KMS charges, slower first scan). The default `"auto"` keeps the old behaviour but marks SSE-KMS/SSE-C objects `etag-opaque` and reports them in `health().details["etag_mode_objects"]` / `["etag_opaque_encrypted_objects"]`, so the exposure is visible. Tested with moto only, not against real KMS. *Status: Partial (closed only when operators choose `content` mode; default remains ETag-based). Mitigation: set `digest_mode="content"` for buckets holding protected data, and alert on `etag_opaque_encrypted_objects > 0`.*

**R33. Connector freshness has no SLA or heartbeat.** `ConnectorRegistry.health_report()` marks stale, failed and never-synced connectors as degraded, and `registry.assert_fresh(ids, policy=FreshnessPolicy(max_lag_seconds, overrides))` raises `StaleConnectorError` listing them. `freshness_guard(registry, ids)` returns a callable for retrieval paths that yields the stale connector ids (empty = fresh). These are opt-in: nothing in the server or SDK calls them, so a silent connector still does not turn decisions into DENY unless the integrator wires the guard in before serving source-derived answers. *Status: Partial (enforcement primitive exists; wiring is the caller's responsibility). Mitigation: call the guard in every retrieval path and pick `max_lag_seconds` from the lease and TTL values.*

**R34. Tokens are digests in memory, plaintext in the file.** The registry stores SHA-256 digests after load, but `ALES_TOKENS_FILE` and the Kubernetes secret hold plaintext tokens. *Status: By design for in-memory. Protect the file and secret as credentials.*

**R35. Separation of duties on approvals.** `POST /v1/approvals/{approval_id}/decide` returns 409 `{"detail": "separation of duties: decider matches requester"}` when the deciding subject equals either the requested principal (the `principal.id` of the `/v1/authorize` call, whose access is pending) or the requesting actor (the token subject that made the call). Both are stored on the approval (`requested_by_principal`, `requested_actor`, migration 0003) and apply to approve and deny alike. Approvals created before migration 0003 have no requester recorded and are not blocked. `ALES_APPROVAL_ALLOW_SELF=1` turns the check off (dev or single-admin deployments; the server logs a startup warning). The check compares subject strings: it cannot tell that two different subjects are the same person, and an `admin` who can mint tokens for other subjects can still collude with themselves. *Status: Resolved (enforced by default; the escape hatch is opt-in and documented in `docs/operations.md`). Mitigation: leave `ALES_APPROVAL_ALLOW_SELF` unset in production; give approvers subjects distinct from every requesting principal and service.*

**R36. Workload identity is opt-in unless `ALES_ENFORCE_WORKLOADS=strict`; the grants gate is opt-in unless pinned.** In the default `auto` mode the resolver checks `agent_id` only for tenants that have registered at least one workload, and checks workload grants (which principal may act as which agent) only for tenants that have recorded at least one grant. A tenant with no workloads is not checked at all: `agent_id` is an unverified label. Without pinning, revoking a tenant's last grant switches its grant check off again. `authorize_ex(..., require_grants=True)` (server: deployment setting) pins the grants gate: when the workload gate is on, a principal with no grant for the agent is denied (`PRINCIPAL_NOT_IN_SCOPE`, audit `grant_missing`) even when the tenant has zero grant rows, so deleting the last grant can no longer disable it. `off` disables both checks (startup warning). *Status: Partial (closed when `strict` + `require_grants` are set). Mitigation: set `ALES_ENFORCE_WORKLOADS=strict` and require grants in production; with `require_grants` every agent-acting principal must hold an explicit grant.*

**R37. Caller-asserted `risk` is advisory.** `risk` on `/v1/authorize` is supplied by the caller, so a caller can lower it to avoid a policy rule keyed on `risk`. `PolicyDocument.risk_floors` (`{purpose or "*": low|medium|high}`) is the trusted control: the effective risk is the maximum of the caller's value and the floors for the request purpose and `"*"`, and a missing caller value counts as the floor. Without a floor the caller's value is used unchanged, and a rule matching `risk` exactly (for example `low`) can still be dodged by a caller who raises the risk above it. *Status: Partial. Mitigation: set floors for every purpose that must be treated as high risk; write deny rules for `high` rather than relying on `low` or `medium` to stay stable.*


## External providers and release gate (v0.4)

**R38. Providers are inside the trust boundary and are an availability dependency.** A required provider that times out, errors, returns a redirect, an oversize or malformed body, or answers UNKNOWN turns the decision into UNKNOWN (`EXTERNAL_POLICY_UNAVAILABLE`), so a provider outage denies every request that reaches it. Provider answers are unsigned: integrity rests on HTTPS plus a bearer token (production enforces both for non-loopback providers; there is no certificate pinning or mTLS), and a compromised provider can ALLOW what lineage allowed but can never loosen a lineage or built-in DENY. Provider latency adds to every decision (bounded by `timeout_s`, parallel across providers). *Status: By design. Mitigation: run providers next to the control plane, mark only policy-critical ones `required`, monitor the audit `status` and `latency_ms` fields.*

**R39. A release receipt bounds the race, it does not close it.** The side effect happens after `/v1/releases` returns. A revocation, policy change or provider change in that window is not seen, and `valid_until` (30 s default) is advisory to the caller. The receipt is stored and audited but is not signed, and nothing in the repo verifies a receipt at the point of execution. *Status: Partial. Mitigation: execute immediately, keep `ALES_RELEASE_TTL_SECONDS` small, make the side effect idempotent, and re-call the gate on retry.*

**R40. Obligations are recorded, not enforced or delivered.** Provider obligations (for example masking) are merged and written to the audit ledger as clipped JSON strings, but the fixed wire responses carry no obligations field, so a caller cannot act on them and ALES does not apply them. *Status: Open. Mitigation: encode must-enforce conditions as DENY in the provider policy until a wire field exists.*

**R41. Provider semantics are per request, not per object.** One provider call covers all objects of a request and its answer restricts every object; a provider cannot allow some objects and deny others. An optional provider's explicit DENY or HUMAN_REVIEW still restricts (only silence or UNKNOWN is skipped). An OPA rule that is undefined is treated as unavailable. Cedar providers are called once per resource (at most 25; more is unavailable). *Status: By design.*

**R42. Action and destination are caller-asserted, and workload gating on releases is opt-in.** `/v1/releases` trusts the caller's `action`, `destination` and `workload` strings; a caller can lie about a destination to obtain an ALLOW for another one. The workload and capability check (`action:<action>`) applies only under the same opt-in gate as `/v1/authorize` (`ALES_ENFORCE_WORKLOADS=strict` plus grants in production). Approvals for provider review bind the destination and provider revisions, but the destination itself is not verified. *Status: Partial. Mitigation: run `strict` workloads with grants, and have the executing component (not the agent) supply the destination.*


## Identity federation (v0.5)

**R43. Bare principal scopes and caller-asserted issuers do not separate two identity systems.** A bare scope entry (`alice`) matches that id under any issuer; only `iss:<issuer>:<id>` entries separate them. `principal.issuer` is supplied by the caller exactly like `principal.id`, so a caller that may claim an id may also claim an issuer. Policy rules and the SDK decision cache key use the bare id (the SDK works around the cache by never caching issuer-bearing requests). Approval fingerprints are issuer-aware since v0.5.1: an approval for `alice` at issuer A no longer covers `alice` at issuer B, and issuerless principals keep their old fingerprints so existing approvals stay valid. *Status: Partial. Mitigation: write new scopes as `iss:` entries, send the issuer from the component that authenticated the user, and write policy rules against `iss:`-aware scopes rather than bare ids.*

**R44. The API caller is not the end user.** The audit actor is the authenticated token subject; the principal in the request is the person the decision is about and is trusted from the caller. An OIDC token's own groups apply only when that token's subject is the request's principal, but a service token with the `read` role can still ask about any principal. *Status: By design. Mitigation: give only the component that authenticated the user a `read` token for that tenant.*

**R45. Entitlements are event-maintained or bounded assertions, not live.** `StaticEntitlements` changes only after `POST /v1/entitlements/reload` ran on each replica (each holds its own in-memory copy; a replica that was not reloaded keeps the old groups, though the epoch bump from another replica invalidates caches). An OIDC groups claim is trusted until the token's `exp` (plus 60 s skew); revoking membership sooner needs the denylist. The reload is process-wide: a tenant admin's call applies changes to, and bumps the epoch of, any tenant whose entries changed. Group names and ids appear in audit records. *Status: Partial. Mitigation: reload every replica from one deploy step, keep token lifetimes short, treat group names as identifiers.*

**R46. The release gate does not resolve entitlements.** *Status: Closed (v0.5.1).* `POST /v1/releases` resolves entitlements exactly like `/v1/authorize` (server-resolved groups, one re-decision when the revision moves mid-call, required-provider outage restricts the verdict, entitlement fields in the audit record). The release body has no `groups` field, so callers cannot assert groups there. Historical: before v0.5.1 a group-only scope was denied at the gate even for a member (fail closed).

**R47. Provider failure is only as precise as the verdict.** With a required entitlement provider down, only verdicts denied solely for `PRINCIPAL_NOT_IN_SCOPE` become UNKNOWN (`ENTITLEMENT_UNAVAILABLE`); an ALLOW is unaffected because groups cannot narrow a scope. The reason code is new: clients and `spec/decision_api.schema.json` that enumerate reasons must add `ENTITLEMENT_UNAVAILABLE`, `principal.issuer` and `groups`. Providers must enforce their own timeouts; the server does not. *Status: Partial. Mitigation: treat UNKNOWN as deny (the SDK does); update schema consumers.*


## Lifecycle value layer (v0.5.1)

**R48. Durable session exposure is voluntary, and reset is host-defined.** ALES learns of an exposure only when an SDK or host reports it (`durable_sessions=True`, or `POST /v1/sessions/{id}/exposures`). A session that was never reported is invisible: it is never flagged and the impact preview says `unknown`, not zero. A reporter that fails keeps the exposure pending only in its own process memory (best-effort; a crash before the retry loses it). `needs_reset` is a flag, not an action: ALES resets nothing, and what a reset means for a runtime (drop the thread, truncate memory, restart the run) is the host's decision. Content already shown to a model or a person cannot be recalled. *Status: By design. Mitigation: enable durable mode in every runtime that serves context, poll `GET /v1/sessions/{id}` (or check on each turn) and treat `needs_reset` as a stop signal.*

**R49. The impact preview is bounded by what ALES knows.** It lists registered lineage, kinds, outbox rows and reported sessions. Copies in stores without a purge handler, caches, prompts, transcripts, exports and other systems that were never registered or reported are not in it (the response carries a fixed `uninstrumented_note` saying so), and a revocation does not touch them. The preview is also a point-in-time read: lineage or sessions can change between the preview and the revocation. *Status: By design.*

**R50. Session flags cover only revocations already in effect, at acceptance.** The flag is raised when a revocation is accepted, and only if it is already effective: a delayed revocation (`effective_at` in the future) flags nothing now and is not flagged again when its time comes. An exposure reported after a revocation landed is not flagged retroactively (its next authorize is denied by the resolver, which is the safety mechanism; the flag is advisory). A scoped revocation flags only sessions that exposed the object to a listed bare principal id; `group:` and `iss:` scope entries are not expanded for flagging. Flagging touches the exposure rows of the current session generation only. *Status: Partial. Mitigation: re-run the SDK `enforce()` check, which uses the resolver and is exact, when a flag matters.*

**R51. Decision explanations mix a recorded verdict with a live graph.** `decision`, `reasons` and `authority` come from the audit record of the decision; dependency paths, causes and cleanup state are read when the explanation is requested, so a tombstone accepted later with an earlier `effective_at` can appear as a cause and cleanup states keep moving. Paths are capped (10 per object). The trace lookup filters `detail.trace_id` inside one tenant's ledger without an index (a Postgres expression index is an operator step, see `docs/lifecycle.md`). Only decisions written to the audit ledger can be explained: nothing is stored for a decision the ledger refused. *Status: Partial.*

**R52. Rebuilt derivatives are unsigned, and handlers are trusted code.** A completed rebuild job registers the new derivative from the server (no envelope signature, `source_system` and `policy_version` copied from the old derivative), outside the signature ingress that guards client-posted envelopes. ALES records the digest a handler returns and cannot verify that it matches content the handler stored, or that the transformation did what its `implementation_ref` claims. Handlers run in the server process (or whatever `create_app(rebuild_handlers=...)` wires): they are as trusted as purge handlers. The new derivative's authority is recomputed from its new parents and checked for widening, so a rebuild cannot grant more than its inputs allow. *Status: By design. Mitigation: keep handlers small and reviewed, store and verify content digests in the integrator's store, treat `rebuild.complete` audit records as the provenance trail.*

**R53. Rebuild planning is level by level, and non-idempotent work is not retried.** A plan covers the direct derivatives of a superseded object that carry a registered transformation; deeper levels are planned when their parent's rebuild completes, so a failed middle level stops the chain until an operator re-posts. Derivatives without a tag are invisible to the planner (they stay `REFRESH`). A transformation not declared `idempotent` is never retried after a handler error or a crashed lease, because the side effect may have happened. *Status: By design. Mitigation: tag derivatives at registration, declare idempotence honestly, alert on `failed` jobs (`GET /v1/rebuilds?state=failed`).*

**R54. Session retention is bounded, not guaranteed.** Exposure and session rows expire `ALES_SESSION_RETENTION` (default 7 days) after the last report and are swept at most once a minute by the worker (lazily ignored in between, and only by reads when no worker runs). After expiry a session is forgotten: it is no longer flagged by later revocations and `GET /v1/sessions/{id}` is 404. A long-lived session must keep reporting to stay covered. Exposures store identifiers only (session id, principal id, context id, version, workload), never content, but session ids and principal ids are personal data in some deployments. *Status: By design. Mitigation: size retention to the longest session you must be able to flag, and treat session ids as identifiers when setting data-retention policy.*
