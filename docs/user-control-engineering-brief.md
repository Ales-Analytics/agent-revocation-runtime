# Ales user control layer for personal and enterprise agents

Engineering decision brief · 20 November 2026 · Proposed architecture

Repository baseline `f92154613486546d49cbc7c8f08849a9fb7ded65`

## What we are building, in plain English

Ales gives an application a way to keep a promise about what an AI agent may do. A person can delegate an action, reserve a decision, change their mind, and move an explicit rule to another compatible application. An organization can restrict the actions available in its workspace, require an authorized reviewer, and withdraw a workload or employee's access. Before an agent takes a covered action, the application checks the actual operation against the rules and authority in force. Another engineer can reproduce a test of whether the application honored the decision.

The deliverables are an open behavioral specification, an embeddable reference runtime, host and tool integration interfaces, and a conformance suite that observes effects. Application teams supply their models, interfaces, workflows, identity systems, and domain tools. The portable object is a scoped, versioned rule with explicit semantics. Credentials, previous approvals, organization records, and a running agent's entire memory have separate ownership and lifecycles.

**Add a sibling action-control contract alongside ALES INVARIANT.** Delegate source-lineage checks to Invariant when an action depends on registered data. Preserve the current release API for existing callers. Start with a small set of enforceable action types and two independently maintained host frameworks. Use the same decision semantics for local and managed deployments.

Consider one rule, “You may prepare a document. I choose who receives it.” On a personal device, a different app can import that rule and ask its owner to select a recipient. At work, an employee can make the same reservation. Their employer can limit delivery to a particular client team and require a data owner to approve restricted documents. The employee chooses among eligible recipients. The data owner signs off on that exact delivery. A later edit to the recipient reopens the decision. An unattended company service has its own grant and deciding roles. Those are three uses of the same machinery, with three identifiable sources of authority.

The defensible research question is narrow. Given the same authenticated facts and mandatory rules, will two hosts preserve a person's reserved choice, invalidate a stale approval, and produce the permitted observable effect or an explicit refusal? Differences in wording, model reasoning, and the actual account privileges on each host remain legitimate. A destination without a provider grant should produce a different verdict with an identifiable reason.

## The architecture

| Component | Responsibility and trust boundary |
|---|---|
| **Rule store and control plane** | Store immutable adopted rules, amendments, withdrawals, authorship and applicable scope. Distinguish private personal, organization-managed and workload-owned rules. Update active revisions atomically using expected revisions. Allow users to preview the effect of an edit. A model-generated interpretation remains a proposal until a permitted actor adopts it. |
| **Portable contract and evaluator** | Evaluate a normalized proposed action against fixed facts and active rules. Produce a verdict, reasons, required choices, relevant revisions and freshness bounds. Support a closed set of typed fields and predicates in the initial profile. Unknown mandatory syntax or an unsupported effect makes the action ineligible for dispatch. |
| **Identity and policy bindings** | Resolve identity, membership, delegated scope, tenant policy, target authority and optional source status through explicit adapters. Keep provider credentials in the credential-owning component. The policy engine is pluggable. The meaning of the decision states is fixed by the profile. |
| **Host and decision interface** | Suspend, present, revise, decline and resume on an authenticated channel. Bind the response to the effect details the user actually reviewed. A renderer may translate or simplify the display while preserving the material alternatives and consequences. Rendering compatibility and actual accessibility need separate evaluation. |
| **Executor and effect adapter** | Normalize values from the actual outbound request, recheck at dispatch, atomically claim the local operation once, call the destination and reconcile its outcome. The trusted boundary must control the credential or mediate every egress path claimed as covered. A hook in an otherwise unrestricted process provides cooperative coverage only. |
| **Evidence and qualification** | Record policy decision, human decision, dispatch and destination outcome as distinct events. Publish versioned, redacted conformance reports. A sampled monitoring trace helps diagnose failures; an independent test destination establishes what it received. |

**Action vocabulary is a first-class engineering deliverable.** A rule such as “ask before external disclosure” requires agreement on what counts as a disclosure, which recipient is external, which fields contain the data, and which adapter can verify those facts. Start with a private draft operation and a directed delivery operation against a controlled service. These distinguish local work from an externally visible write while keeping the test oracle tractable. Each extension declares operation semantics, material arguments, possible external effects, visibility, supported preconditions and readback. An opaque script cannot inherit the guarantee of a typed adapter.

**The portable rule and the local grant have different lifetimes.** A contract binds owner, workspace, action type, applicable resources, predicates, mandatory limits, reserved choices, revision and supersession. A local binding identifies destination account, trusted principal, provider grant, adapter version and available capabilities. An approval binds the actual arguments and recipients, tenant, workload, actor, policy and rule revisions, option selected, validity window and use count. With a new destination or material argument, issue a new decision. A provider can still refuse execution. Use the repository's canonicalization support for bounded structured data and an explicit procedure for domain normalization before fingerprinting. A digest identifies bytes; it cannot establish the truth of a caller's claims.

### Composition rules

Distinguish two forms of transfer. A shareable template gives the recipient an independent copy to inspect and adopt, without the originator's private state or ongoing editing rights. Two hosts enforcing one owner's live rule need an authoritative revision source and a documented freshness policy. An exported snapshot alone cannot communicate a later withdrawal. Test both cases, including a disconnected host reconnecting after the owner changed a rule. At a tenant boundary require an explicit export decision, import validation and destination grants. Use synthetic samples in shareable templates.

1. Establish the authority mode and tenant. Verify the actual actor and workload. Invalid identity or an absent necessary grant blocks execution.
2. Apply the resource owner's restrictions, organizational ceilings where applicable, and mandatory personal or workload limits. Any applicable prohibition wins. Treat missing mandatory facts or engine errors as indeterminate and withhold the effect.
3. Collect unsatisfied obligations. A human approval is an obligation with an authorized actor, scope and validity. Multiple independently required approvals accumulate. Contradictory mandatory obligations that cannot be satisfied together yield an explicit blocked decision.
4. Apply soft preferences only among the remaining permitted choices. A default or inferred preference cannot supply mandatory approval. A valid user edit can tighten a rule immediately at its authoritative store; relaxation may require another local grant.
5. Re-evaluate at dispatch and when resuming after interruption. A host can use a signed or locally trusted snapshot only within the declared freshness profile. For sensitive enterprise writes, require a current authoritative check. Publish the remaining source, identity-provider and in-flight exposure windows.

### Failure and concurrency contract

A proposal may be held for a decision, denied, unsupported, indeterminate or ready. A ready proposal can expire. A claimed execution may be confirmed, rejected or have an unknown outcome. A host restart must preserve which state was durably recorded. Use a transaction for local approval consumption plus operation identity and a durable outbox or equivalent dispatch ledger. Enforce uniqueness across concurrent workers. If a destination supports idempotency, reuse the same operation key on a supported retry. If it supports authoritative readback, reconcile a lost acknowledgement. If neither is available, retain “outcome unknown” and require reconciliation. Unlimited retries risk duplicate writes.

A local transaction cannot make an independent provider part of an atomic commit. Validate resource preconditions inside the destination when it supports them and describe remaining races per adapter. Distinguish “withdrawal acknowledged at the rule store,” “all enforcement replicas have observed it,” and “an external operation has already committed.” This is especially important after employee offboarding, policy rollback, restore from backup and failover. [MIT on delivery acknowledgement and duplicate suppression](https://cyber.harvard.edu/openlaw/msdoj/endtoend.pdf)

## Two deployment profiles

| Requirement | Individual or personal workspace | Enterprise workspace |
|---|---|---|
| Rule ownership | User controls adopted rules and private bindings in their workspace. Export only the selected rule scope. | Tenant controls managed rules, allowed export, retention, and domain restrictions. Preserve the distinction between organization requirements and decisions reserved to an employee. An employee's personal workspace is a separate boundary. |
| Identity and authority | Local account or authenticated host session plus a separate grant at each supported service. | Federated issuer/subject and tenant, distinct workload identity, resource audience, entitlement revision and delegated or app-only mode. Never silently replace an expired delegated token with broader app-only credentials. [Microsoft Entra authority modes](https://learn.microsoft.com/en-us/entra/agent-id/authorization-agent-id) |
| Human decisions | One person can reserve a decision, decline, amend, withdraw or grant limited standing authority. | Explicitly model employee, manager, data owner and administrator as distinct roles. Support named deciding roles, separation of duties, reviewer reassignment and deprovisioning. Verify reviewer eligibility again when the action is dispatched. |
| Unattended agents | Standing delegation specifies resource, allowed effect and expiry. Unsupported decisions pause. | A service-owned workload may run without a user. Its authority comes from a governed workload grant with sponsor, scope, audience and expiry. A new employee's permission or the sponsor's identity cannot be assumed. |
| Storage and deployment | Embedded evaluation, local durable state and OS-protected secrets. Remote checks require connectivity; define which read-only operations remain available offline. | Begin with a single-tenant self-hosted deployment, Postgres, managed keys/secrets, tenant-scoped logs, externally authenticated services and explicit operator roles. Multi-tenant SaaS requires independent isolation, restore, key separation and load qualification. |
| Policy lifecycle and evidence | The user can inspect what changed and why an action was held. | Version and approve policy changes, support dry-run comparison and staged rollout, preserve an audit history and correlate provider outcomes. A rollback activates a new auditable revision. Gate any exceptional administrative path independently and disclose coverage. |

**Enterprise identity lifecycle.** Use OIDC for application authentication and OAuth for delegated provider access. Where supported, rich authorization requests express a structured grant. SCIM can deliver provisioning changes, but receipt of an offboarding event does not prove every cached decision and downstream token has expired. Keep an authoritative local suspension mechanism, tenant-scoped epochs and bounded cache lifetimes. A self-hosted Keycloak deployment is a practical repeatable identity fixture. Entra can be an additional provider qualification when a test tenant is available. [OAuth security BCP](https://www.rfc-editor.org/rfc/rfc9700.html) · [Rich Authorization Requests](https://www.rfc-editor.org/rfc/rfc9396) · [SCIM protocol](https://www.rfc-editor.org/rfc/rfc7644) · [Keycloak administration guide](https://www.keycloak.org/docs/latest/server_admin/index.html)

**Enterprise privacy and operations.** Record identities, revisions and effect references at the minimum granularity needed to verify a decision. Keep payloads and human-readable personal rules out of general telemetry by default. Scope access to audit records separately, encrypt tenant material, define retention and deletion behavior, and test restoration against a newer revocation epoch. A hash of a predictable recipient or small set of options can reveal its value; use opaque references or tenant-keyed commitments where correlation is needed. Expose provider latency, stale-revision rejection, pending decisions, unknown outcomes and audit-write failures as operational metrics. [OpenTelemetry handling of sensitive data](https://opentelemetry.io/docs/security/handling-sensitive-data/) · [OPA decision-log masking](https://www.openpolicyagent.org/docs/management-decision-logs)

## Qualification, test oracle and release gates

**Access for people who need help using software has its own evidence requirement.** In UK government research, 35% of surveyed UK adults reported helping someone with digital activities in the previous year. A Microsoft Research study in India documented the roles of literacy, privacy and infrastructure in smartphone use. Anthropic's field report on Claude Code found that more experienced users both delegated more freely and interrupted more often. These are different populations. Together they motivate testing assisted setup, independent correction and interruption as distinct operations. [UK digital inclusion report](https://www.gov.uk/government/publications/how-people-are-helped-online-informal-and-proxy-digital-support/informal-and-proxy-support-for-digital-inclusion-final-report) · [Microsoft Research field study](https://www.microsoft.com/en-us/research/publication/sophistication-with-limitation-understanding-smartphone-usage-by-emergent-users-in-india/) · [Anthropic autonomy report](https://www.anthropic.com/research/measuring-agent-autonomy)

Give two reference clients the same held decision. Let a participant inspect a sample, change a rule, predict its effect on a fresh example, and move it to the second client. Include keyboard and screen-reader use, a supported second language, and assisted setup followed by independent use. On a shared device, test that the helper's session cannot approve for the owner after handover. In an enterprise client, test whether the employee can distinguish a personal reservation from a restriction only the organization can change. Record mistaken approvals, unrecognized recipient changes, independent correction and later reuse. Keep the participant study separate from machine certification. A runtime test cannot establish that someone understood the choice.

Run three configurations against the same independently logged target: the host's native controls; native controls plus a stock policy backend; and the proposed Ales profile. Include WebAgentica's existing fixture results as a portability comparison, then run equivalent supported cases on a pinned build. Publish observed differences, unsupported cases and harness failures. If existing code already passes a requirement, reuse it and publish the interoperability test. Separate a shared reference evaluator passing in two hosts from an independent evaluator passing the same vectors.

| Mandatory case | Observable acceptance criterion |
|---|---|
| User declines or renderer lacks a mandatory choice | Zero target dispatches. Renderer exposes decline or declares unsupported. Approving an unrelated request cannot release the held action. |
| Amendment or policy change while approval is pending | Old approval cannot release a materially changed operation. Current rule, user choice and organization policy are independently identifiable. |
| Change target, tenant, recipient, arguments or approving role | Inapplicable approval is rejected. The target's received parameters agree with the normalized, approved operation on valid cases. Include a legitimate-allow control to catch implementations that deny everything. |
| Transfer personal rule to another host or workspace | The destination preserves the rule's meaning, evaluates its own policies, and obtains an independent valid grant. A package carrying origin credentials or managed private data fails the export/import profile. |
| Source withdrawn, employee disabled, or workload suspended | After the declared freshness boundary, subsequent covered writes are withheld. Measure propagation, pending work, in-flight residuals and cached decisions separately. Test manager loss of approver role and cross-tenant identity collisions. |
| Conflict between organizational and individual rules | Tenant prohibition still blocks after user approval. Tenant allowance still pauses for a user's reserved choice on delegated work. App-only work never borrows that user's standing approval. Two-person review rejects self-approval. |
| Restart, duplicate delivery, partition or concurrent consumers | Reconcile durable claim and target state. For adapters claiming idempotency, verify one effect. For unsupported recovery, expose unknown outcome without blind retry. Test a crash on both sides of the remote write. |
| Missing policy facts, evaluation errors or obligations | Report indeterminate or unsupported; target receives zero writes where a mandatory check is unresolved. Include a positive control for an explicitly optional input. |
| Framework, model or interface changes | Given identical verified facts and mandatory rules, admitted effects and required choices remain within contract. Test a real framework resume and two presentation channels. Model variability is reported separately from deterministic control violations. |

Compatibility reports should carry profile/version, dependency digests, security and freshness configuration, credential placement, tested operations, evidence type and unsupported paths. A schema check, an in-process fake, a live host with a controlled target and a real provider tenant are distinct evidence classes. For each run, report unauthorized dispatches, false blocks, missing decision prompts, duplicate effects, unresolved outcomes, decision latency percentiles, throughput and revocation-to-denial windows. For performance, record hardware, dataset, contention, cache state and provider latency. Set deployment-specific latency and availability targets from measured baselines. For functional conformance, require **zero prohibited dispatches in the published mandatory fixtures**. No finite fixture set proves general safety.

### Order of work

1. **Baseline and threat model.** Pin the two host SDKs and policy engine, model covered credentials and dispatch paths, and run the native-control comparison. Produce an inventory of what already works and where behavior diverges. Preserve the baseline as CI fixtures.
2. **Core contract and independent oracle.** Freeze the first action and decision schemas, rule precedence, approval identity, export semantics, error taxonomy and lifecycle. Publish input/output vectors and a plain-language state table before both SDKs depend on the same code.
3. **Personal profile.** Implement the reference evaluator and durable execution path. Qualify real host A and host B on a transferred rule, changed parameters, held choice, withdrawal and restart. Provide a locally reproducible run without a hosted Ales account.
4. **Managed enterprise profile.** Add a single-tenant deployment, OIDC fixture, organizational policy provider, distinction between delegated and app-only work, two-party approvals, onboarding/offboarding, audit and operational recovery. Qualify the same core semantics plus enterprise-specific tests with real Postgres and at least two concurrent workers.
5. **Publish compatibility releases.** Require an implementation maintained or reproduced outside the reference-runtime team, a versioned coverage report and a rerunnable CI artifact. Promote an adapter only when its claimed enforcement and outcome evidence are present. Require separate qualification before advertising multi-region operation, strong cross-replica freshness or a particular live provider.

## What compounds

Every material discrepancy becomes an executable regression against a named host, adapter, policy-engine version and effect. Every independent implementation makes the public contract less dependent on the reference code. Every framework or provider upgrade reruns the same evidence. The resulting record answers a reusable engineering question: **which version, under which operating conditions, demonstrably preserves which decisions?** Kubernetes Gateway API provides a credible precedent for publishing conformance by supported features and implementation. [Gateway API conformance](https://gateway-api.sigs.k8s.io/docs/conformance/)
