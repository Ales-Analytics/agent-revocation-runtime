# Ales Recall and the first market for revocable agent work

Founder decision memo · 20 November 2026 · Proposed product direction

**Build a recall system for work produced by AI agents.** When a customer withdraws access to a source, Ales should tell an application which saved answers, drafts and paused jobs depend on it, stop the affected work at its next covered use, and show which work can safely continue. When a source is corrected, Ales should help the application rebuild the affected work from current inputs. Keep `ales audit` as the free way to discover whether a particular workflow can keep that promise.

The first sale is much narrower. Find a legal-software vendor whose enterprise customer has excluded restricted matters from an AI rollout. Sell the vendor a way to demonstrate that its own application honors a change of matter access across search, cached answers and resumed work. Put the customer's security reviewer in the acceptance meeting. The commercial outcome is permission to ship that workflow.

## The first five minutes of the product

A deal team uses an assistant to prepare a comparison of two transactions, Birch and Cedar. Maya can access both when she starts. The assistant retrieves documents, saves a mixed-matter draft, warms an answer cache and pauses for review. Overnight, the firm removes Maya from Cedar. Another reviewer, Dev, retains access to both.

The next morning Maya opens the draft. The application explains that its sources have changed and offers to prepare a Birch-only comparison. The old mixed draft stays unavailable to her, including through its cache entry and the paused job. Dev can still open it if the source versions remain current and the other policies allow it. The Birch-only replacement starts with fresh authorized inputs and an empty model context. Asking the model to edit the old draft would put Cedar back into the process. An unrelated case continues through the same application.

The customer sees the source-change time, when Ales learned of it, which destinations observed a block, when authorized work recovered, and whether any releases occurred in between. If someone downloaded yesterday's draft, the operator sees the recorded delivery for follow-up. Information already delivered to a person, an external service or a model lies beyond the recall boundary.

The **valuable second half** of this product is letting people keep working. Deleting every thread on every permission change is easy to explain and expensive to use. Preserving authorized work gives the application owner a reason to deploy the control and a measurable alternative to clearing all state.

## Why this window exists

**A deployment actually depended on this capability.** In its October 29 launch account, Harvey says Eversheds Sutherland initially excluded restricted matters. The firm's IT team tested inheritance from iManage Security Policy Manager before bringing those matters into its firmwide rollout. Harvey enforces matter restrictions on threads, vaults, review tables and spaces, including mixed-matter sharing. This is evidence for a buyer's decision and evidence that a vertical incumbent can solve it internally. The prospect for Ales is a builder facing the same question across components it operates. [Harvey and Eversheds Sutherland](https://www.harvey.ai/blog/ethical-walls-harvey-imanage)

**A different collaboration policy can be intentional.** In Glean's team-chat beta, new retrievals respect the requesting teammate's permissions. Text already brought into a shared thread can be reused by teammates who lack access to the source. Ales must make the choice visible at integration time. The first profile should preserve source restrictions. A later sharing profile would require a separately authorized release to a named audience, with its own owner and lifetime. An ordinary YAML override must never silently turn the first behavior into the second. [Glean team-chat permissions](https://docs.glean.com/user-guide/assistant/team-chat)

**Persistent work is becoming a platform primitive.** Google describes long-running agents and enterprise use of its Memory Bank. Anthropic describes agents making progress across multiple context windows using persistent artifacts. The inference for Ales is that an increasing share of the work an agent uses today may have been created under yesterday's permissions. A model upgrade alone cannot tell the host whether a checkpoint is still authorized. [Google Cloud platform announcement](https://cloud.google.com/blog/products/ai-machine-learning/whats-new-in-gemini-enterprise-agent-platform) · [Anthropic engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)

**The clouds already handle much of the easy case.** Bedrock Managed Knowledge Base can perform source-aware access checks for supported connectors. AWS documents that Salesforce access removals can take minutes and distinguishes inspecting synchronized ACLs from fetching content. Microsoft documents the permissions its SharePoint indexer supports and its dependence on change notifications and successful processing. If every read goes directly to a supported source and the application retains nothing, the native solution can win on simplicity. Ask a prospect to name the first durable object beyond that boundary. [AWS connector matrix](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-acl.html) · [AWS Salesforce behavior](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-ds-salesforce-acl.html) · [Microsoft indexer](https://learn.microsoft.com/en-us/azure/search/search-indexer-sharepoint-access-control-lists)

Support software is a plausible second market. Intercom already refreshes several connected sources within minutes and lets customers find conversations in which content was involved. A source-to-conversation dashboard would be a weak reason to switch. An independent support-AI vendor with customer-owned caches and pending case actions could still value a verified correction. Start in legal because there is a named rollout decision tied to the specific behavior. [Fin source refresh](https://www.intercom.com/help/en/articles/7837535-fin-ai-agent-faqs) · [Fin content reporting](https://www.intercom.com/help/en/articles/7837533-fin-ai-agent-reporting)

## Where the code creates an opening

LlamaIndex's ingestion pipeline can remove a missing source from its document and vector stores under its delete-enabled strategy. LangGraph's Postgres saver deletes checkpoints by thread, and its store interface supports memory outside a single thread. LangChain's generation-cache lookup accepts a prompt and model configuration. All are sensible interfaces. None of those identifiers alone tells a host which saved thread, cache record and recipient depend on a newly restricted matter. The application can implement that mapping itself. Ales must demonstrate that it costs less to integrate and maintain across upgrades. [LlamaIndex ingestion code](https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/ingestion/pipeline.py) · [LangGraph Postgres saver](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint-postgres/langgraph/checkpoint/postgres/__init__.py) · [LangGraph store](https://github.com/langchain-ai/langgraph/blob/main/libs/checkpoint/langgraph/store/base/__init__.py) · [LangChain cache interface](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/caches.py)

Zep already documents provenance metadata, filters on retrieval and removal of affected memory. A closed Graphiti issue provides a concrete historical engineering example. A contributor reported that removing an episode could both leave its contents in summaries and remove facts separately supported elsewhere. The lesson is to test continued authorized use alongside removal. Treat the issue as a report on the named releases. [Zep memory security](https://help.getzep.com/v3/memory-security) · [Graphiti issue 2034](https://github.com/getzep/graphiti/issues/2034)

## The contract customers would install

1. **Observe the authority.** A customer-selected connector supplies tenant, source and policy revisions, the affected principals, the reason, and its observation time. Track its cursor, reconcile skipped events, and handle reordering. Distinguish permission loss for one user, global withdrawal, and replacement of source content. Only the last has a natural successor version. If the source offers no trustworthy commit clock, report that interval as unknown.
2. **Capture dependencies at creation.** Record versioned references for all inputs exposed to the operation, including restored messages, tool results and cached context. Bind the output to the union of those inputs. Keep customer content and identity mappings in the customer's environment. Treat pseudonymous identifiers, graph edges and timestamps as sensitive metadata. A customer approves any evidence export.
3. **Check at the last covered use.** Re-evaluate the intended principal, purpose, recipient and current parents before serving a cached answer, constructing a resumed prompt, or handing a draft to a destination. Reject missing or expired evidence under the restricted-matter profile. Distinguish an already released stream prefix from subsequent output. Tight dispatch bounds require cooperation from the component that can actually make the delivery.
4. **Recover selectively.** For a corrected source, propagate invalidation to dependent work and schedule registered, idempotent transformations. For a principal-specific change, keep shared material available to eligible users. A Birch-only replacement is a newly authorized job with a new output and its own lineage. Use structural checks plus human acceptance for substantive legal content. Identical output text from a model rerun is neither required nor a test of authority.
5. **Give the buyer independently checkable evidence.** Include application build and adapter digests, profile version, fixture, expected paths, observed source revision, destination observations, positive controls, timing bounds and missing paths. Give the buyer an offline verifier and a way to run the case using native controls or its own implementation. An in-toto statement can bind evidence to the build under test. Customer-controlled signing keys and an independently operated receiver make the trust assumptions inspectable. [in-toto statement format](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md)

**What can vary.** Teams choose their source of authority, identity mapping, storage engine, host framework, tenant policy, eligible recovery actions and freshness budget. Support a versioned profile with typed configuration along those dimensions. Profiles that weaken a required property receive a different identity and require a new acceptance run. Every covered release of registered sensitive work requires current authority over every required input within the declared freshness bound. Provider grants, on-premises operation and hosted models can change independently.

**What the clock means.** Record source commit, connector observation, gate enforcement, last observed stale release, first successful authorized recovery and acknowledged physical cleanup separately. Give each clock an owner and record uncertainty. An in-flight decision and an unobserved source change create different exposure windows. A partition that exceeds the freshness budget holds protected work and counts against availability. Measure both stale releases and wrongful denials. Permanent deletion, backups and third-party retention need their own scope.

**What could make it uneconomic.** A widely used template can become an ancestor of millions of drafts. Eagerly regenerating every descendant after each edit could swamp the customer's inference budget. Under the proposed design, stale work becomes ineligible on its covered path, then a queue rebuilds active work on demand under a budget. Test a heavily shared ancestor, a slow source and a long-idle case. Measure the longest queue wait, decision cost and unnecessary rebuilds. Some customers may rationally prefer clearing state and starting again.

## A pilot designed to lose to a better alternative

Choose one vendor with a real paused workflow, an application engineer who controls its delivery path, and a security reviewer who can name the rollout decision. Use the identity provider or matter system already authoritative for that customer. Start in its test tenant using two synthetic matters, two reviewers, a real LangGraph Postgres checkpoint, a warmed application cache, and a receiver controlled by someone outside the Ales implementation team.

Compare **the customer's best native configuration**, **native controls plus clearing affected sessions or all state**, and **Ales-mediated selective recall** on the same fixture. Give the native implementation the same opportunity to recheck rights on resume. Include the time needed to integrate, maintain and explain each option. For a buyer that can simply disable persistence, measure the resulting workflow and latency as a fourth baseline.

| What changes | Observable result required |
|---|---|
| Maya loses Cedar after the mixed draft is cached and the job pauses | After the agreed freshness boundary, no Cedar-bearing fixture reaches Maya's covered prompt or receiver. Dev can still use the same draft if otherwise eligible. An unrelated job succeeds. |
| A source is corrected for everyone | The old version stays withdrawn. A new draft cites the successor inputs, passes the fixture's content checks and receives an independent ID. Record time and compute spent on recovery. |
| An event arrives late or twice, or a replica restarts while work is pending | Reconciliation detects divergence. A stale or unknown path is reported. Recovery creates at most one accepted replacement per job and destination, or an explicit manual-review case where acceptance cannot be established. |
| A declared path has no observer, or the source clock is unavailable | The report marks that path or interval unknown. A missing observation cannot become a pass. A positive delivery control verifies that the receiver and its observation window actually worked. |

Pre-register the boundary with the buyer. For illustration, a pilot might require zero out-of-bound releases across 100 randomized change/resume orderings on two application instances, every authorized control delivered, and added p95 under a buyer-agreed latency budget. Publish the counts per path and the worst observed lag. A hundred correlated runs do not establish a universal failure rate. Include integration person-days, clean-regeneration cost, and reviewer time alongside the technical results.

## How the business could compound

**The strongest distribution idea is to let the buyer own the test.** A law firm's platform team can put the same mixed-matter acceptance case in its next two vendor reviews. Either vendor can pass using native controls. A vendor that lacks a cheap way to pass can adopt Ales. If the reviewer asks for current evidence on each material framework upgrade, demand recurs without requiring every vendor to standardize on Ales's runtime. Validate that reviewers will actually reuse a test before investing in a certification business.

| Keep open and portable | Sell and maintain |
|---|---|
| The invariant, versioned evidence format, offline verifier, reproducible fixtures, capability declarations and a usable self-hosted reference path. Respect the existing Apache-2.0 baseline. [Repository license](../LICENSE) | Version-qualified integration releases, managed reconciliation and recovery, private deployment support, compatibility testing across upgrades, fleet evidence history and contractual response to integration failures. |
| Customers own policies, documents, traces and keys. A competing implementation can pass the same case. | Ales can keep its connector qualification infrastructure, release automation and independently developed operational tooling private. Grow the regression corpus with public upstream changes, synthetic fixtures and customer cases only under explicit rights. |

Every supported source/host/store combination adds maintenance cost. Start with one combination and track the engineering hours to qualify each upgrade. A library of passing combinations becomes an advantage only when the next one costs less to support, reviewers reuse the result, and customers renew when the framework changes. The open algorithm and signatures are readily reproducible. An independently trusted test, installed integrations and a maintained history of real upgrade behavior are harder to reproduce together.

For pricing discovery, propose a fixed-fee pilot for one named workflow and an annual fee per supported production application or environment with a usage band. Charging for every denial would penalize the behavior the buyer wants. Estimate value from engineering days spent per review, repeated reviews per year and the cost of waiting on the blocked deployment. Compare that figure with Ales's qualification and support costs. Record a paid commitment and the budget owner's name before treating interest as demand. The size of this independent market remains an open question.

| Window | Work and owner | Decision |

The upside reaches beyond legal research. The same source-change event could eventually identify support replies awaiting dispatch, analytical summaries needing regeneration and agent handoffs awaiting fresh authorization. Each expansion earns its place by identifying an owner, a durable piece of work and an observable release. The first test of that ambition is whether one firm's security reviewer trusts the evidence enough to release one previously withheld workflow.
